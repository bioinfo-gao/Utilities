# fastp

## 大文件跑到 ~99.5% 处卡死，且**可复现地停在同一输入位置** —— 实测 v1.3.3

**症状**：进程还在、`ps` 看 `%CPU` 还挺高，但**输出文件停止增长**，几十分钟不动。

**实测现场（2026-08-11，proj29 `29_Keqiang_Xie_wgs_5_vectors`）**

- 跑法：**3 个 fastp 实例并发**，每个 `--thread 8`，输入是 26–30 GiB 的 gzip FASTQ
  （人 WGS PE150），源在 `/Work_bio`（机械/网络卷），输出到 `/mnt/ex_8T_SSD`。
- 结果：**最小的那个样本正常完成（exit 0）**，另外两个在写出约 **93%** 时卡死，
  分别冻结 20 min / 16 min 后被人工发现。
- 取证：
  | 判据 | 值 |
  | :--- | :--- |
  | 主线程 `/proc/<pid>/wchan` | `futex_wait_queue` |
  | 工作线程 wchan | 全部 `hrtimer_nanosleep`（fastp 的队列空转轮询） |
  | `/proc/<pid>/io` 的 `read_bytes` / `write_bytes`，45 秒内 | **零变化** |
  | 输出文件 mtime | 冻结 20+ 分钟 |

**⚠ 头号误判点：`ps -o %cpu` 是进程生命周期的平均值，不是瞬时值。**
卡死的进程 `ps` 显示 387%，会让人以为"它在忙"。要用 `top -b -n 2` 取瞬时值
（实测只有 65% / 21%，而且是空转轮询），**真正的硬证据是 `/proc/<pid>/io` 两次采样零变化** ——
mtime 可能因文件系统缓存而不敏感，`io` 计数器不会骗人。

**⚠ 反向陷阱（2026-08-12 实测补充）：`/proc/io` 零变化**不能单独判卡死** ——
健康的纯计算阶段长得一模一样。**

| | fastp 卡死 | bwa-mem2 `index` 建 BWT（完全健康） |
| :--- | :---: | :---: |
| 产物增长 | 零 | 零（数十分钟不写盘） |
| `/proc/io` 45 s | 零变化 | **零变化** |
| **CPU ticks 45 s** | **零增长**（在等锁） | **4501 / 满载 4500** |
| `wchan` | `futex_wait_queue` | `0`（running） |
| RES | 平稳 | 57.7 GB（在内存里建 suffix array） |

⇒ **`CPU ticks（/proc/<pid>/stat` 第 14+15 列）才是"在算 vs 在等"的分界**，
必须与 io 一起看。ticks 在涨就绝不能报死锁 —— 只按"io 零变化 + 产物零增长"判，
会把 bwa-mem2 索引这种正常阶段误杀。看门狗实现见
`29_Keqiang_Xie_wgs_5_vectors/scripts/15_watchdog_run_all.sh`（四判据版）。

**判据（照抄可用）**
```bash
p=<pid>
cat /proc/$p/wchan                       # futex_wait_queue ?
for t in /proc/$p/task/*; do cat $t/wchan; echo; done   # 全是 nanosleep ?
awk '/_bytes/{print}' /proc/$p/io; sleep 45; awk '/_bytes/{print}' /proc/$p/io   # 两次一样 = 无进展
```
三条同时成立 = 卡死，不是慢。（CLAUDE.md 的规则是 wchan + mtime 两条；
**加上 `/proc/io` 零变化这第三条更可靠**，建议以后都取这一条。）

**⚠ 根因：不是并发争用（这条已被证伪，别再照第一版结论去改并发）**

第一版结论写的是"3 实例并发争用"，并据此改成**串行 `-w 12`** 重跑 —— **同一个样本又卡死了**，
而且停在**几乎同一位置**：

| | 首轮（3 并发 × `-w 8`） | 次轮（串行 `-w 12`） | 差 |
| :--- | :---: | :---: | :---: |
| 输出 R1 字节 | 24,743,374,248 | 24,740,493,231 | **0.01%** |
| 进程 `read_bytes` | 59,637,395,456 | 59,334,955,008 | **0.5%** |
| 输入总字节 | 59,637,092,591 | 同左 | 停在 **~99.5%** 处 |

**同一样本、两种并发模式、停在同一输入位置 ⇒ 数据驱动，与并发无关。**

## ⚠ 第三轮实测（2026-08-12）：「输入 gz 损坏」这个头号怀疑**已被证伪**

上面那句"首要怀疑对象是输入 gz 流被截断/损坏"**是错的，别再照它排查**。同项目续测：

| 检验 | 结果 |
| :--- | :--- |
| 8 个原始 FASTQ 全量 `gzip -t`（含卡死的 L6，单文件 950–5500 s） | **8/8 全部通过**，无一报 `unexpected end of file` |
| 在 `gzip -t` 通过**之后**再跑第三次（单样本、`--thread 12`、`--detect_adapter_for_pe`） | **又卡在同一位置**，`futex_wait_queue`，空转 **19 h 39 min** 才被发现 |

**⇒ 输入完整，根因在 fastp 1.3.3 自身**（接近输入尾部时的线程/队列死锁）。
三次尝试：3 并发 ×`-w 8` → 串行 ×`-w 12` → 单样本 ×`-w 12`，**全部停在 ~99.5%**。
`--dont_eval_duplication` 也不解决。

**排查顺序（已按第三轮结果改写）**
1. **先比对两次卡死的 `read_bytes`**。位置一致 ⇒ 与并发无关；位置随机 ⇒ 才考虑并发/资源。
   这一步最便宜，却最容易被跳过 —— 第一次就跳过了，白白改并发重跑了一小时。
2. `gzip -t <input.fastq.gz>` 全量校验。**通过 ≠ 问题解决** —— 它只排除"数据损坏"这一个分支，
   排除完就该直接跳到第 4 条，不要像我一样在数据方向反复打转。
   （反过来若真不通过，那确实是数据问题，结论钉死。）
3. 同批次里**跑成功的样本**是天然对照。⚠ 但注意本例中成功的 H43 恰好是**最小**的文件，
   "小文件成功"很容易被误读成"大文件=数据坏"，实际只是没触发到那个 bug。
4. **确认输入完整后就不要再跟 fastp 纠缠** —— 它没有断点续跑，每次重试成本是数小时。
   直接换路：`--adapter_sequence` 显式给接头（跳过 `--detect_adapter_for_pe`）、
   换 cutadapt/trim_galore、或**评估这一步是否必需**。
   本例结论：WGS 插入位点/拷贝数分析**不必 trimming** —— bwa-mem2 自带 soft-clip，
   接头序列比不到载体 contig 上、不会伪造整合位点（proj13 走 sarek 同样默认不 trim）。
   代价是接头含量高的样本跨接头 read 灵敏度较低，属**假阴性**方向，报告写明即可。
   **这条是本次真正省下时间的决定** —— 与其修 trimming，不如先问它该不该存在。

**规避**
1. **拿到大批 FASTQ 后、开跑之前，先全量 `gzip -t` 一遍**。比在流程跑到 99% 时卡死再回头查便宜得多。
2. 长跑必须带**停滞哨兵**：每 5 min 查输出增长，连续 3 次零增长就报警并打印各进程 wchan。
   范例：`29_Keqiang_Xie_wgs_5_vectors/scripts/4b_fastp_rerun_sequential.sh` 的 `stall_sentinel`。
   实测价值：首轮靠人眼 20 分钟才发现，次轮哨兵 15 分钟就报警。
3. fastp **没有断点续跑**，卡死只能整样重跑 —— 哨兵越早报警省得越多。
4. 半成品**移走隔离、不要删**（CLAUDE.md「原始记录不能丢」）；重跑脚本**另建新文件**，
   不要在原脚本上原地改 —— 正因为保留了首轮的隔离产物，才能做上面那张"两次停在同一位置"的对照表。
