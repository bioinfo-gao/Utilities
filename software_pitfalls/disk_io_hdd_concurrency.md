# 机械盘上「并发读/并发复制」是负优化 —— 实测 7 倍差距

**一句话**：HDD 只有一组磁头。N 路并发读 N 个大文件 = 磁头在 N 个磁道组之间来回寻道，
**顺序读退化成随机读**；吞吐不是持平而是**成倍下降**。固态盘没有寻道，才能靠并发吃满带宽。

## 1. 实测数据（P46，2026-11-25，10 个 59–76 GiB 的 WGS BAM，源盘 `/srv/external_data` = sdc，`rotational=1`）

| 读取方式 | 聚合吞吐 | 相对单路 | 读延迟 r_await | 队列深度 |
| :--- | :---: | :---: | :---: | :---: |
| **单路顺序复制**（`cp` 一个文件） | **175 MB/s** | **1×** | 255 ms | 1.55 |
| 3 路并发复制（3 个 `cp` 同时跑） | 76 MB/s | 0.43× | — | — |
| DELLY 直读 BAM，2 路并发 | 40 MB/s | 0.23× | 117 ms | 3.14 |
| DELLY 直读 BAM，6 路并发 | 24 MB/s | 0.14× | 128 ms | 11.75 |
| 更早：HC 22 路 + DELLY 10 路 + 扫描 4 路（共 36 个读者） | 21–27 MB/s | 0.15× | **85–128 ms** | **24.97** |

**同一块盘、同一批文件，并发度从 1 升到 6，吞吐掉到 1/7。**
注意 r_await 在单路时反而最高（255 ms）——那是因为单路在吃满带宽、每个请求都是大块传输；
**判断盘是否被打爆要看「队列深度 + 聚合吞吐」，不能只看单个请求的延迟。**

## 2. 怎么判断"卡住了"还是"在等盘"

- 进程 `%CPU` 只有 1–9% 而 `wchan=futex_wait_queue` / `pipe_read`、`/proc/<pid>/io` 的
  `read_bytes` 仍在涨 ⇒ **在等盘，不是死锁**。
- `top` 的 `wa`（iowait）是全局指标：P46 实测 36 个并发读者时 iowait **39%**、CPU 空闲 43.8%
  —— 这种组合（CPU 闲 + iowait 高）就是 I/O 过订阅的签名。
- `iostat -dx <dev> 10 2` 取**第二段**（第一段是开机以来的均值，没有意义）。

## 3. 三条可操作的规则

1. **CPU 预算（如 ≤56 线程）管不住磁盘并发度。** 它们是两种独立资源。
   P46 实测：三个 stage 的 CPU 合计仍在预算内，却因 36 路并发读集体变慢到 1/7。
   **排程时必须单独记「此刻有几个进程在读同一块 HDD」。**
2. **大文件搬运一律单路。** 要并行的是"复制"和"计算"这两件**不同**的事，不是复制本身。
   见下节流水线模式。
3. **CPU 空闲不构成启动新 I/O 密集任务的理由。**（P46 犯过：看 CPU 空闲 78% 就重启 DELLY，
   结果它整小时 0–3% CPU 纯等盘，还把别的 stage 一起拖慢。）

## 4. 推荐模式：复制/计算流水线（producer-consumer）

当计算要反复随机读同一个大文件（SV caller、变异检出、BAM 扫描）而数据在 HDD 上时：

```
1 路生产者：顺序复制 file[i] 到 SSD → touch .staged/<id>        （吃满 HDD 顺序带宽）
N 路消费者：抢占一个 .staged 的 id → 在 SSD 上计算 → 删除该副本  （吃满 CPU）
生产者领先不超过 MAXSTAGED 个 ⇒ 限制 SSD 峰值占用
```

- 消费者抢占用 `mkdir <claim>/<id> 2>/dev/null || continue`（目录创建是原子的，比 flock 简单可靠）。
- 复制后**必须校验字节数**（`stat -c%s` 源 vs 目标）；残缺副本要能识别并重copy。
- 删除**只删自己刚复制出的副本**，且路径必须在暂存目录下 —— 原件绝不碰。
- 参考实现：`/home/gao/projects_2026Q4/46_park_wgs/scripts/27_stage4b_delly_pipelined.sh`
  （同目录 `26_..._ssd_staged.sh` 是**反例**：每个 worker 串行「复制→计算→删」，
  复制的 36 min 里 CPU 空闲 91%，计算时 HDD 空闲，两种资源互等）。

## 6. 测吞吐时的两个坑

1. **页缓存会虚高**：刚读过的文件再 `cp` 一次可能测出 340 MiB/s（P46 实测），
   而换一段未读过的区域只有 175 MiB/s。**要么用全新文件，要么取稳态窗口**（文件已复制过半时测）。
2. **`ps -o %cpu` 是进程生命周期均值**，长任务会把当前状态平均掉 ⇒ 判断"此刻在不在算"
   必须用瞬时值：`top -bn1`，或自己取 `/proc/<pid>/stat` 第 14+15 字段做差。
