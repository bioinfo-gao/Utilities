# Symlink vs Bind Mount — 优劣对比

小型参考笔记，基于本机实际案例：`projects_2026H2` 用的是 **bind mount**
（`/dev/sda1[/projects_2026H2]` 挂载到 `/home/gao/projects_2026H2`），
`projects_2026M7` 用的是 **symlink**（`/home/gao/projects_2026M7` -> `/mnt/ex_8T_SSD/projects_2026M7`）。
两者都能做到"物理存储在别处、逻辑上挂在家目录下"，但机制和适用场景不同。

## 本质区别

- **Symlink（软链接）**：一个特殊的文件系统对象，内容就是"目标路径"这个字符串。访问时由文件系统在
  内核层做一次路径重定向（`readlink`/自动 follow）。是一个**独立、持久的文件**，本身就存在磁盘上。
- **Bind mount**：内核 mount namespace 层面的操作——把某个已存在的目录（源）**重新挂载**到另一个路径
  （目标），让两个路径指向同一个 inode/目录树。不创建任何新文件，**是运行时状态，不是文件**。

## 对比表

| 维度                            |                                                                    Symlink                                                                    |                                                            Bind Mount                                                            |
| :------------------------------ | :--------------------------------------------------------------------------------------------------------------------------------------------: | :------------------------------------------------------------------------------------------------------------------------------: |
| 创建是否需要 root/sudo          |                                                              否，普通用户权限即可                                                              |                                     **是**（`mount` 系统调用需要 `CAP_SYS_ADMIN`）                                     |
| 重启后是否保留                  |                                                            是（本身是磁盘上的文件）                                                            |                                     **否**，除非写入 `/etc/fstab` 或用系统服务持久化                                     |
| 对程序是否透明                  |        否——`stat()`/`lstat()` 能看出是 link；部分工具（如 `rsync` 默认、某些备份/同步软件）对 symlink 有特殊处理，可能不 follow        | **是**——挂载后几乎所有程序、库、系统调用都当成普通目录，无法用常规文件 API 区分（只能查 `/proc/mounts`/`mountinfo`） |
| IDE / GUI 文件浏览器可见性      | **常不显示 link 标记**（本机 CLAUDE.md 就记过这个坑——Positron/VS Code 文件树看不出这是 symlink，只有 `ls -la` 的 `->` 箭头能看出） |                                               完全看不出来，视觉上和普通目录零差别                                               |
| 能否跨文件系统/磁盘指向任意路径 |                                          能，指向任何路径（包括别的磁盘、别的用户目录，只要有读权限）                                          |                                      能，但源和目标都是"已存在的目录"，不是"任意字符串路径"                                      |
| 只读挂载                        |                                                 不支持（symlink 没有独立权限位，权限跟随目标）                                                 |                                   支持`mount --bind` + `mount -o remount,ro`，可做只读暴露                                   |
| 配置/迁移成本                   |                                                 极低——`ln -s` 一条命令，改目标只需删了重建                                                 |                           较高——通常要写`/etc/fstab` 或 `mount` 命令，多机器/重装系统要重新配置                           |
| 删除方式                        |                         `rm` 掉 link 本身，目标数据不受影响（常见新手误区：`rm -rf link/` 加尾部斜杠有风险，见下）                         |                                          `umount` 卸载挂载点，源目录数据同样不受影响                                          |
| 典型坑                          |        尾部加`/` 时某些命令（`rm -rf symlink/`）会进入目标目录操作，而不是删 link 本身；部分程序看到 symlink 会拒绝跟随（安全策略）        |  忘记`/etc/fstab` 持久化，重启后目标路径"消失"变回原来的空目录，容易造成"数据丢失"的假象（其实数据在源目录，只是没重新挂载）  |

## 什么时候选哪个

- **选 Symlink**：单机、临时/个人范围内的"快捷方式"，不需要 root，希望将来换目标（换盘/换路径）时
  改一下链接就行；`ls -la`/`readlink` 就能一眼看出真实位置。**本项目 `projects_2026M7` 属于这种场景**——
  纯粹是"把 SSD 上的目录在家目录下露一个入口"，没有必要用需要 root 的 bind mount。
- **选 Bind Mount**：需要对外完全"以假乱真"——某些程序/容器/chroot 环境要求路径看起来就是真实目录、
  不能是 symlink（部分工具会拒绝跟随 symlink，或者备份/同步逻辑对 symlink 有特殊而非预期的处理）；
  需要跨用户/跨服务共享同一份数据、且愿意承担一次性的 root 配置成本换取"零程序兼容性问题"。
  `projects_2026H2` 当初大概率是这类考虑（或纯粹历史原因），且已经稳定运行，无需改动。

## 一句话结论

两者都能实现"物理在别处、逻辑在家目录"，但 **symlink 更轻量、免 root、显式可见（前提是用 `ls -la`
而非 GUI）**；**bind mount 更"隐形"、对程序更透明，但需要 root 且默认不持久化**。没有 root 权限
或不需要对程序完全隐藏链接关系时，symlink 是更简单的默认选择——这也是本次新建 `projects_2026M7` 时
选 symlink 而不是照搬 `projects_2026H2` 的 bind mount 方式的原因。
