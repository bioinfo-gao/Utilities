# Nextflow 项目磁盘回收 — 三方案实证对比

**创建日期**: 2026-07-29（文件名日期不可变，后续修订在本文档内部追加"更新记录"）

## 0. 背景与起因

`/Work_bio` 用到 97%（8.3T / 9.1T，仅剩 321G 可用）。最初的两个直觉方案是：

- 方案 A：直接删掉 `projects_2026H1` 整个文件夹
- 方案 B：把这个文件夹压缩起来

先做实测再决定，结果是**两个直觉都不是最优解** —— 存在一个方案 C，拿到方案 A 87% 的收益，
却几乎不付方案 A 的代价。

---

## 1. 三方案实测对比

`projects_2026H1` 总量 **5.5 TiB**（`du -sh`；`--apparent-size` 同为 5.5 T，无稀疏文件差异）。

| 方案 | 可省空间 | 操作后 `/Work_bio` 可用 | 代价 |
| :--- | :---: | :---: | :---: |
| A. 整个文件夹删除 | **5.5 TiB** | ~5.8 T | 交付物、脚本、报告、`.nextflow.log` provenance 全丢 |
| B. 整个文件夹压缩 (gzip/tar.gz) | **~0.4–0.5 TiB（仅 ~8%）** | ~0.8 T | 数天 CPU，换来极少空间；且此后每次读取都要解压 |
| **C. 只删 Nextflow `work/`（采用）** | **4.76 TiB（87%）** | ~5.5 T | 仅失去该 run 的 `-resume` 缓存 |

**方案 C 拿到了方案 A 的 87% 收益，代价却只是"重跑不能 resume"。**

## 2. 为什么压缩（方案 B）这么不划算 —— 文件类型普查实证

全目录 271,832 个文件的体积按类型汇总（`find -printf '%s\t%f'` + awk 归类）：

| 类别 | 体积 | gzip 预计可省 | 说明 |
| :--- | :---: | :---: | :--- |
| BAM | 2804.1 GiB | ~30 GiB (~1%) | BAM 本身就是 BGZF/DEFLATE，已压过 |
| fastq.gz | 1966.0 GiB | ~0 | 已 gzip |
| bedGraph | 192.4 GiB | ~165 GiB (~86%) | 纯文本，高度可压 |
| text/tabular (txt/tsv/csv/log/json/html/gtf/bed) | 175.9 GiB | ~155 GiB | 纯文本 |
| `.tmp`（sortingcollection / temp-core-*.sam） | 125.8 GiB | — | **应该直接删，不是压缩** |
| `.sst` (RocksDB) | 62.2 GiB | 部分 | 内部已部分压缩 |
| `.dat` | 41.8 GiB | 部分 | 混合 |
| bigWig | 35.8 GiB | ~0 | 已 zlib 压缩 |
| `.ctab` (StringTie) + `.tab` | 59.4 GiB | ~50 GiB | 纯文本表 |
| fasta（未压缩） | 26.1 GiB | ~18 GiB | |
| singularity `.img`/`.sif` | 23.5 GiB | ~0 | squashfs 已压缩 |
| 其他（index/rds/h5/pdf/png/py/pyc/so…） | 剩余 | 少量 | |

**核心事实：5.5 T 里 87% (4.77 T) 是 BAM + fastq.gz 这两种已压缩格式，gzip 对它们完全无效。**
真正可压的只有 ~480 GiB 文本类内容，就算全部压到 ~15%，总收益也只有 ~0.4–0.5 TiB（约 8%）。

### 2.1 那个看起来很诱人但要避开的选项：BAM → CRAM

理论上 BAM→CRAM 无损重编码可再省约 40%，即 **~1.1 TiB**。但：

- 这是**格式转换**，不是压缩；需要每个样本正确的 reference genome，弄错就是静默数据损坏
- 2.8 T BAM 的重编码 CPU 代价巨大
- **而且在本例中完全是白费功夫** —— 见下节，这些 BAM 里 89% 本来就该直接删掉

### 3.1 决定性的一条证据

把 BAM + fastq.gz 按"是否在 `work/` 路径下"拆开：

| 位置 | BAM + fastq.gz 体积 |
| :--- | :---: |
| 在 `work/` 里 | **4242 GiB** |
| 不在 `work/` | 528 GiB |

**占满磁盘的那 4.7 T 已压缩数据里，89% 是中间产物。** 这就是"压缩没意义、删除才有意义"的根因 ——
不是因为它压不动（虽然确实压不动），而是因为**它根本不该留着**。

### 3.2 `work/` 里还躺着的纯垃圾

顺手确认的几类，进一步说明 `work/` 无保留价值：

- `*.img.pulling.*` —— singularity 镜像**半截下载**残留（最大单个 1.8 GiB）
- `sortingcollection.*.tmp`、`temp-core-*.sam-*.tmp` —— Picard/aligner 排序临时块，合计 125.8 GiB
- STAR index 的 `SA` / `SAindex` / `Genome` —— **同一套索引存了 3 份**（每套约 28 GiB），且随时可重建
  （`2026_Item2_0205_Jitu` 下 `scripts/work/41/…/star/SAindex`、`scripts/work/37/…/star/SAindex`
  和 `output/genome/index/star/SAindex` 三份并存）

## 4. 标准操作（今后每次优先执行）

用户 2026-07-29 确立：**绝大部分工作用 Nextflow，磁盘吃紧时每次都优先执行方案 C。**

配套脚本：[`reclaim_nextflow_work_dirs.sh`](reclaim_nextflow_work_dirs.sh)

```bash
# 1) 先 dry-run 看能回收多少、都是哪些目录
./reclaim_nextflow_work_dirs.sh /path/to/projects_root

# 2) 确认无误后真删
./reclaim_nextflow_work_dirs.sh /path/to/projects_root --execute
```

脚本的安全设计（每一条都有实证理由）：

1. **默认 dry-run**，必须显式 `--execute`
2. **marker 校验** —— 只删「同级存在 `.nextflow.log` 或 `.nextflow/`」的 `work` 目录，避免误删任何
   恰好叫 `work` 的普通文件夹。本 repo 11 个目标全部通过校验
3. **manifest append-only 日志** —— 删前把「删了哪些目录、各多少字节、df before/after」写进
   `reclaimed_work_dirs_manifest.log`，事后可查
4. **只删 `work/` 自身** —— `.nextflow.log`（provenance / execution trace）、`.nextflow/`、
   `output*`、`results*`、`scripts/` 一律不碰
5. **运行中的 nextflow 直接拒绝执行**

### 4.1 前置检查清单

- [ ] `ps` 确认无运行中的 nextflow（脚本自动做）
- [ ] 目标项目**已交付 / 已结项** —— 删掉 `work/` 后 `-resume` 失效，重跑等于从头跑
- [ ] `.nextflow.log` 保留（体积极小，是唯一的执行 provenance 记录）
- [ ] 长任务放 tmux —— 4.76 T / 27 万文件的 `rm -rf` 要跑一段时间；好消息是中途打断只是少删几个目录，
      不会留下半损坏状态

### 4.2 什么时候**不该**删

- 项目还在跑，或还可能需要 `-resume` 续跑
- 分析口径还没定、可能要改参数重跑上游步骤（此时 cache 值钱）
- `work/` 里有某个步骤的产物**没有**被 `publishDir` 复制到 `output/` —— 删之前先确认交付物完整

## 5. 脚本开发中踩到的坑（已修）

**闸门 1 自匹配**：最初的 nextflow 运行检测写成宽泛的 `ps -eo cmd | grep -iE '[n]extflow'`，
而脚本自身路径是 `.../Server/nextflow_pipeline/reclaim_nextflow_work_dirs.sh` —— 命令行里就含
"nextflow"，于是脚本**永远拒绝执行自己**。

修法：匹配真正的启动命令形态（`(^|[[:space:]/])nextflow([[:space:]]|$)`、
`nextflow.cli.Launcher`、`nextflow-*-one.jar`），并排除 `$$` / `$PPID` 自身进程。

教训：**进程存活检测的 grep 模式，必须窄到不会匹配到检测脚本自己的路径。**
放在 `nextflow_pipeline/` 这种带工具名的目录下时尤其容易中招。

## 5.2 `--maxdepth 4` 默认值漏删（重要，务必记住）

第一轮执行后做交付后自查，发现一处数字对不上：

| 项目 | 事前预估「除 work 外」 | 事后实际剩余 | 差 |
| :--- | :---: | :---: | :---: |
| `2026_Item5_T.majus` | 98 G | **175 G** | **+77 G** |
| 其余 7 个项目 | — | 与预估**逐一吻合** | 0 |

根因：脚本原本默认 `find -maxdepth 4`，而这里有一个**深度 5** 的 work 目录：

```
2026_Item5_T.majus/cleaning_and_make_ref/working_split/WhS4_4/work   ← 78 GiB，被漏掉
```

这是"**先按样本分片、每片各跑一条独立 pipeline**"的常见布局（`working_split/<sample>/` 下各自带
一套 `.nextflow.log` + `.nextflow/` + `work/`）—— `work/` 会埋得比 `<project>/scripts/work` 深得多。

之所以能发现：事前用 `du -sh --exclude=work` 估算「除 work 外的体积」，而 `du --exclude` 是
**匹配任意深度**的，`find -maxdepth 4` 不是。两者口径不一致，事后对账时差额就暴露了。

**修复**（已改入脚本）：

- 默认**不限深度**；`--depth N` 变成可选的收窄参数，不再是默认值
- 加 `-prune`：匹配到 `work/` 后不再往里递归，避免嵌套 work 被重复计数

**方法论教训（比这个 bug 本身更重要）**：
用**两种口径不同的方法**分别算同一个量（`du --exclude` 任意深度 vs `find -maxdepth` 限深），
然后**逐项对账**——这才是这个 78 G 漏删被抓到的原因。如果只看「df 释放了 4.8 T，符合预期」
就收工，这 78 G 会一直躺在那里，而且下次换个项目还会照样漏。
**别只验证总量对得上，要逐项对账。**
