## 1. 起因与目标

用户原话：**"我的目标是腾出 `/mnt/ex_8T_SSD/` 的空间，这是我的主力高速工作盘。"**

`projects_2026H2` 已是历史归档（新项目走 `projects_2026M7`），却仍占着这块 SSD。
最初的指令是"整体转移到 `/srv/external_data`"，但先做勘察后发现：**光搬不删是下策** ——
2.4 T 里 65% 是可直接回收的 Nextflow `work/`，搬过去等于把垃圾原样换个盘堆着。

## 2. 勘察：一个容易看漏的 bind mount 结构

```
/mnt/ex_8T_SSD/projects_2026H2   ← 真实物理位置 (sda1)
        │ fstab bind
        ▼
/home/gao/projects_2026H2        ← 日常使用的路径
```

**`/home/gao/projects_2026H2` 不是普通目录，也不是软链接，而是 fstab 里的 bind mount**
（`/etc/fstab` 第 17 行）。这个事实决定了整个方案，因为：

仓库里有 **1387 条绝对软链接**指向 `/home/gao/projects_2026H2/...`
（Nextflow task 目录之间 stage 输入用的链接）。**只要这个路径本身保持不变，它们就全部继续有效。**
所以最终选择"改 bind mount 的源"而不是"把目录换成软链接"——
路径字符串一个字节都不变，1387 条链接零改动。

work_B 内容构成：

| 内容 | 体积 | 性质 |
| :--- | :---: | :--- |
| `clips_<sample>.fa` | 503.4 G | **TIDDIT 的 soft-clipped reads FASTA**，从不发布 |
| 中间 BAM | 230.0 G | BWAMEM2_MEM 未去重 BAM，已被 `output_B/*.md.cram` 取代 |

## 5. 第三步：切换 bind mount（需要 root）

### 5.1 先清空挂载点占用

`umount` 会被任何 cwd 在挂载点内的进程挡住。实测有 7 个：

| 进程 | 处理 |
| :--- | :--- |
| 2 个旧 tmux session（`RNA` / `claude_science`，6 月建的，里面只有 idle bash） | `tmux kill-session` |
| 3 个 Positron IDE 集成终端的 bash（36 天前开的） | SIGTERM **无效**（交互 shell 忽略 SIGTERM），改 **SIGHUP** 才退出 |
| 1 个 2026-06-23 启动的旧 `claude` 会话 | SIGTERM 即退 |
| tmux server 本身（cwd 在 `5_mouse-rRNA`，且托着本次的 rsync） | 留到最后，rsync 跑完再 kill session，server 随之退出 |

> **坑**：`fuser -vm <挂载点>` 给的是**设备级**结果，会把同一块盘上其他目录的用户
> （这里是 `projects_2026M7`）和 swapfile 都列进来，虚报一倍。
> 真正挡 umount 的判据是 **`readlink /proc/*/cwd` 落在挂载点路径下**。
>
> **坑**：`tmux new -s RNA` 那个进程其实是 **tmux server**，本次任务自己的 session 也挂在它下面 ——
> 中途 kill 它会连带杀掉正在跑的 rsync。

### 5.2 切换命令

```bash
# 1. 建最终父目录并搬入（同盘 rename，瞬间）
sudo mkdir -p /srv/external_data/gao_projects
sudo chown gao:gao /srv/external_data/gao_projects
mv /srv/external_data/gao_projects_offload/projects_2026H2 /srv/external_data/gao_projects/
rmdir /srv/external_data/gao_projects_offload

# 2. 改 fstab（先备份）
sudo cp /etc/fstab /etc/fstab.bak_0730
sudo sed -i 's|^/mnt/ex_8T_SSD/projects_2026H2 |/srv/external_data/gao_projects/projects_2026H2 |' /etc/fstab
grep projects_2026H2 /etc/fstab

# 3. 卸载 → 源端静止 → 最后一次增量同步 → 挂上新位置
sudo umount /home/gao/projects_2026H2
rsync -aHAX --numeric-ids /mnt/ex_8T_SSD/projects_2026H2/ /srv/external_data/gao_projects/projects_2026H2/
sudo mount /home/gao/projects_2026H2

# 4. 确认（SOURCE 必须是 sdc1）
findmnt -T /home/gao/projects_2026H2
```

**把最后一次增量同步夹在 `umount` 与 `mount` 之间**：那一刻源端已经没有任何路径能被写入，
同步窗口为零。这不是多此一举 —— 见 §6.1。

### 6.1 一个必须搞清楚而不是绕过的"失败"

第 4 项一直报差异，反复同步也不消失：

```
.d..t...... .git/
>f..t...... .git/FETCH_HEAD
>f..t...... .git/index
.d..t...... .git/objects/
```

**根因：源仓库还是"活的"**。IDE 的 git 扩展在后台周期性 `git fetch`，
每隔几分钟就刷新 `FETCH_HEAD` 的 mtime。（这是从 mtime 规律跳动**推断**的 ——
autofetch 是瞬间结束的周期进程，没抓到进程实例，不是实证。）

逐条核实后确认全部良性：

| 文件 | 判定 |
| :--- | :--- |
| `.git/FETCH_HEAD` | md5 **完全一致**（`7ec1204…`），上游无新提交，只刷了 mtime |
| `.git/index` | md5 不同，但它是 **stat 缓存**（记录每个文件的 inode/device）—— 跨文件系统复制后 inode 必然变，任一侧跑一次 `git status` 就各自重写。不含唯一数据 |
| `.git/` `.git/objects/` | 上述两者导致的父目录 mtime 变化 |

git 层面的决定性证据：**HEAD 相同、`show-ref` 全量 diff 为空、对象数完全一致**
（6360 loose / 623 in-pack / 5 packs）。

处理方式：把这几条写成脚本里的**白名单单独打印**，而不是放宽判据 ——
真正的数据差异（`>f++++` 只在源端 / `s` 体积不同）必须仍然报 FAIL，不能被这些噪音掩盖。

> **教训**：迁移一个"活着"的目录时，校验永远不会自然变干净。
> 正确做法是**把每一条差异查到根因、分类白名单**，
> 而不是"看着像无害的就跳过"，也不是反复重跑期望它自己消失。
