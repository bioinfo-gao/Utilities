## 1. 沟通方式

- 内部文档和交谈默认使用中文沟通，各专业术语保留英文。
- 先给结论，再说关键原因、风险和下一步。
- 不确定的信息要标明假设，不要把推测写成事实。
- 需要用户做决定时，只提出会实质影响结果的关键问题。
- 不使用“应该没问题”“大概可以”等模糊表达代替验证结果。
- **没有做过的检查，不得写成带有结论意味的句子。** 缺输入就写“未提供 / 未做，两个方向都不下结论”，
  不要写成看似结果的描述。反例：“客户参考里不含骨架”会被读成“已查明没有骨架残留”——
  应写“客户未提供骨架序列，故未筛查”。
- 客户材料里出现**未定义的缩写**时，按「读法 + 判定依据 + 已排除的其他读法」存档进项目文档，
  供日后回溯；不要只在当次对话里解释一遍就算了。

## 2. 开始任务前

- 先阅读与任务直接相关的文件、现有规则和项目文档。
- 先确认目标、输入、限制条件和完成标准。
- 简单任务直接执行；涉及多个文件、架构变化或高风险操作时，先给简短计划。
- 发现工作区已有用户修改时，保留并理解现状，不覆盖、不回退无关改动。
- 需求存在多种合理解释时，优先采用改动最小、可回退的方案；差异会显著影响结果时先询问。

## 3. 最小修改原则

- 只修改完成当前任务所必需的文件和代码。
- 不进行与当前任务无关的重构、格式化、依赖升级或目录调整。
- 不为了追求“更优雅”而改写已经稳定工作的代码。
- 不擅自改变对外接口、数据结构、交互方式或视觉风格。
- 修改前说明准备调整的文件和原因；范围发生扩大时，先解释原因。
- 优先复用项目已有组件、工具和模式，不平行创建第二套实现。
- 只有小范围修改无法修正错误，或者只有大范围修改才能大幅度提高性能或者准确性的时候，可以主动推荐，我批准后再执行

## 4. 安全边界

- 不读取、输出、复制或提交密钥、令牌、密码和生产凭证。
- 未经明确确认，不删除文件、目录、用户数据、迁移记录或历史记录。
- 未经明确确认，不覆盖现有配置，不执行批量替换和破坏性迁移。
- 未经明确确认，不安装或升级依赖。
- 如必须使用 `--force`、`--no-verify` 或绕过权限的方式解决问题，必须得到用户明确授权且风险已说明。
- 高风险操作前必须说明：将执行什么、影响范围、是否可回退、回退方式。

## 5. 编码与排错

- 先查明根因，再修改；不要用隐藏错误、吞掉异常或注释测试的方式让表面结果通过。
- 命令失败时先阅读完整错误信息，不连续盲试。
- 不为未出现的问题增加无关复杂度。
- 保持项目现有代码风格、命名方式和目录结构。
- 新增依赖前先确认现有依赖或标准库无法合理完成任务。
- 修复 Bug 时，能补回归测试就补；不能补时说明原因。

## 6. 验证与完成标准

- 代码运行结束不代表任务完成，必须重新对照原始需求。
- 运行与本次修改直接相关的测试、类型检查、代码检查或构建。
- 优先运行范围最小的验证，再根据风险扩大验证范围。
- 不声称没有运行过的测试已经通过。
- 验证无法执行时，说明阻塞原因、已完成的替代检查和残余风险。
- 检查是否意外修改了无关文件。

## 7. Git 规则

- 默认允许读取 Git 状态和差异，用于理解现有修改。
- 不回退、覆盖或清理用户已有修改。
- 不执行 `git reset --hard`、`git clean`、强制推送等破坏性命令。
- 未经明确请求，不创建提交、不修改提交历史、不推送远端。
  - **「明确请求」是按轮给的**（2026-08-04 裁定）：用户在本轮说了"直接 commit"之类才算授权，
    且只对本轮有效；**没说就是没有**。不存在常设免问授权。
  - 无授权时：只读 `git status` / `diff` / `log`；改动留在工作区，在回复里说明
    "改了哪些文件、未提交、等授权"。
- 用户要求提交时，提交前先展示变更范围和验证结果。
  - 即 `git diff --cached --stat` 或 `git status --short` + **本次实际跑过的验证及结果**，
    不要只问一句"要不要提交"。
- 即使已获本轮授权，`push`、force-push、改写历史、`reset --hard`、`clean` 仍须逐次先说明再执行。
- 不碰不是自己做的改动：工作区里用户或其他工具（如 Aider）的修改一律保留，不暂存、不回退、
  不扫进自己的提交。
- **仓库 public/private 可见性保持原状**（2026-08-04 用户决定）：不改、不建议改、不再提起。
  照常 commit/push 即可，不必每次重提可见性风险。

## 8. 交付格式

完成任务时按以下顺序汇报：

1. 结果：最终完成了什么；
2. 修改：涉及哪些文件和关键变化；
3. 验证：实际运行了哪些检查，结果是什么；
4. 风险：仍未解决或无法验证的内容；

## 9. 对外交付与署名（**只准备，不发送**）

用户是署名的高级科学家，对外发出的东西带的是**用户本人的签名**。因此：

- **任何以用户名义对外的内容（客户邮件、研究报告、数据交付），一律只准备、不发送。**
  必须由用户逐字过目后，由用户本人发出。**不存在“AI 写完直接发出去”这个选项。**
- Agent 不得代为发送、代为投递、或把内容写入任何会自动外发的位置。
- **邮件**：可以起草并在对话里展示；需要落到草稿箱时，**新增一封，保留用户原稿不动**，
  绝不覆盖或删除用户已写的草稿。任何情况下不执行发送。
- **报告 / 交付目录**：可以完整生成，但**“已生成”不等于“可发出”**。
  汇报时必须把「已完成、待过目」与「已发出」明确分开说，不得混为一谈。
- **主动降低过目成本**（这是本条的配套义务，不是额外服务）：交付前给出
  **逐条主张 → 数据来源**的对照，并把内容分成两栏——
  - **实测事实**：可直接核对，给出文件路径 / 复核方式；
  - **我的判断与推理**：明确标注这是推断而非实测，列出关键假设，
    并单独点出需要用户拍板、或用户可能不同意的争议点。
- 用户提出“我要先看”“先别发”时，不再追问、不再劝说，按只准备处理。

## 9.5 作图 —— 同一张图内多 panel 的配色（**永恒要求**）

**读者默认「同色 = 同义」。** 一张图里两个 panel 用同一组颜色，读者必然当成上下对照来读；
若它们语义其实不同，这就是直接误导，比配色难看严重得多。

- **语义相同**（同一变量、同一分组，需要上下对照）→ **必须**共用同一套配色，图例只出现一次
  或明确标注共享。
- **语义不同** → **必须**用**互不相交**的配色族，并在各自图例/标题写明这组颜色代表什么。
- **默认色环是头号陷阱**：matplotlib / ggplot2 在每个 axes 上都从 C0/C1/C2 重新开始，
  **会静默地**让第二个 panel 拿到与第一个 panel 相同的颜色。**多 panel 图必须显式指定颜色。**
- **出图后自查**：列出每个 panel 实际用到的颜色，检查两集合是否相交；相交且语义不同 = 必须改。
  **最好写成代码里的硬断言**，撞色直接报错不出图。
- **图例不用 `loc="best"`**：分组少时它会把图例塞进绘图区中央压住数据。固定放在绘图区之外。
- **多 panel 图每一张都要人眼看过再交付**，不能看一张就推断其余正确。
- 事故（2026-08-04 项目26）：上面板 蓝/橙/绿 = 区段类型，下面板柱子走默认色环也是 蓝/橙/绿
  但表示样本。用户原话：「同一个图上下两个 panel 意思绝对不同，但用了同一配色，我当然以为是
  上下对照的读」「我作为专家都看糊涂了，客户一定看不懂」。

## 9.6 绝不否定之前的提交（除非确有实质性错误）

**用户原话（2026-08-04）：「除非有实质性错误，永远不要否定之前的一个提交，这回给我带来
无穷无尽的麻烦。当然有原则性错误，应该承认和道歉。」**

一旦在新报告里写"上一份的结论不成立"，客户会顺势质疑那份报告里的**其他所有结论**，
终端客户会质疑整个项目，随之而来的解释、复核与商务代价全由用户承担。
**默认口径：新一轮是延伸/细化，不是纠错。**

**判据 —— 什么算实质性错误：**

| 情形 | 是否实质性错误 |
| :--- | :---: |
| 旧报告把结论当**事实断言**，现证明是错的 | **是** |
| **数值错误超出舍入误差**，且改变结论或量级 | **是** |
| **坐标差异**：版本 / 0-based vs 1-based / 参考不同 / 比对口径不同 | **否**（说明来源与口径即可） |
| 旧结论**本来就带保留**（"most consistent with"），新数据给出更确定答案 | 否 |
| 旧**数据类型**本就分辨不了该问题，新数据类型能分辨 | 否 |
| 旧报告**自己就建议做这项后续确认** | 否（最明显的一类） |

**坐标单列的理由**：坐标不一致绝大多数源于版本 / 0-1 offset / 参考 / 比对口径，属口径差异不是算错。

**推荐词汇（用户给定）**：加强证据 / 更强的证据 / 细化分析 / 进一步分析 / 延伸分析 / 后续分析 /
得出更加确定性的结果 / 强化 / 细化 / 推进一层 —— **强化、细化、进一步，而不是否定。**

**措辞对照：**

| ❌ 禁用 | ✅ 改写 |
| :--- | :--- |
| "requires a revised interpretation" | "the confirmation recommended earlier has now been carried out" |
| "inconsistent with what the earlier report proposed" | "resolves it one level further than the earlier data type could" |
| "not the X previously proposed" | "rather than the X the earlier measurement was equally consistent with" |
| "this changes our recommendation" | "this refines the recommended method" |
| "nothing is superseded **except** …" | "that report is unchanged **and its findings stand**" |

**⚠️ 这条不是让你隐瞒发现。内容照给、一个字不减，改的只是归因框架。**
若确有原则性错误，**必须主动承认并道歉**，说明影响范围与补救，不得淡化、不得埋在正文深处。

## 9.7 拆分交付包 / 取子集 —— 聚合统计量必须逐包重算

**拆包、取子集、增删样本之后，报告里所有"跨样本算出来的数"必须按新范围重算。**
逐样本的数据文件可以按文件名自动路由、按行拆分并自检守恒；**聚合统计量不会跟着文件走。**

- 需重算的典型表述：`N–M` 型**范围**、**计数**（"all six"/"12 windows"/"in every sample"）、
  **均值/中位数/合计**、**极值**、基于集合的**百分比**。
- **每个子集单独核，不能核一个推断其余。** 事故（2026-08-04 项目26）：六样包拆成两包，
  一份报告里的范围仍是六样合并值，而它**恰好等于另一个子集的真值** ——
  "错误碰巧对上"，抽查一个包会得出"没问题"的错误结论。
- **拆分脚本的自检要覆盖"报告里的数字"**，不能只查"数据文件的行"：本次行数守恒与
  零交叉污染全部通过，却发现不了报告里的陈旧聚合值。
- 同样适用于增量分析：加/减样本后，旧报告引用的范围与计数同样失效。

## 10. 原始记录不能丢 —— 修正前必须归档旧版（**一切修正的标准要求**）

**作为数据科学家，原始记录不能丢。错误的那一版正是“改动是否真的改对了”的唯一对照物。**

### 10.0 铁律：永不原地删除或覆盖已产出的结果

- **任何结果目录一律不许 `rm -rf`**，包括以“干净重跑”“清理中间产物”为由。
  重跑前**先移走/复制走**，再跑。
- **“干净重跑”这个理由本身就是错的** —— 它把不可再生的原始记录当成了可再生的中间产物。
- **产出文件名尽量带时间戳或版本号。** 事故实证：同一项目里带时间戳的日志全部幸存、
  不带版本的结果目录被一条命令清空。这不是巧合，是设计差异。
- 长流程要提供**重跑前归档守卫脚本**，由编排脚本自动调用；**单步重跑也必须先调用**。
- 事故（2026-08-03，项目 26）：第一轮 run 的全部 `analysis/` 产物（24 组 BAM/FASTA/
  比对视图/上下文证据）被 `rm -rf analysis tmp` 删除，从未进 git，**永久丢失**。

### 10.1 归档要求

用户要对照“正确的”和“错误的”，才能判断改动是否真的改对了。因此：

- **任何修正（图、表、报告、代码）在覆盖旧版之前，先把旧版原样归档**，与新版并存可对照。
  **绝不允许直接覆盖后只留新版。**
- 归档位置：项目内 `superseded_for_comparison/`（**目录名用英文**），按
  `<产物类型>/v<N>_<YYYYMMDD>_<缺陷简述>/` 分版本存放。
- **同时存下产生该版本的脚本快照**，命名标出版本，使“错在哪”可以直接 `diff`，不依赖记忆。
- 目录里必须有 `README.md` 索引：每版**缺陷是什么、怎么改的、来源（原始产物 or 重生成）、
  怎么并排对照**。
- **区分“原始产物”与“重生成”**：能从 git 取出原始文件的，直接取；原始文件已被覆盖、只能用
  当时的脚本重跑的，**必须在 README 里写明这是复现、不是当初那个文件本身**。
- **归档内容一律不进客户交付目录**，交付目录只放当前正确版本。
- 归档是修正动作的一部分，不是可选步骤；报告修正时一并说明旧版归档在哪。
