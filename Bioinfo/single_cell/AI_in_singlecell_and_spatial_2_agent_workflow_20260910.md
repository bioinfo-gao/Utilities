## §0 结论先行

> **能交给 agent 的，是"做错了能被机械检出"的工作。
> 不能交的，是"做错了看起来一模一样"的工作。**

**这条判据比"任务难不难"有用得多。** 写一个 500 行的管线脚本很难，但跑一遍就知道对不对——
**可以交**。从一张图里读出 12 个数值填进表格很简单，但读错了没有任何迹象——**不能交**。

**⇒ 因此本篇的核心不是"agent 能力清单"，而是"闸门清单"（§4）。**

## §1 基准现实：先把期望值调对

**2026 年已经有针对性的基准，结论一致地不乐观** **【检索】**：

| 基准 | 规模 | 结果 |
| :--- | :---: | :---: |
| **单细胞 omics agent 基准** | **50 个真实分析任务**，跨多组学/物种/测序技术 | Grok3-beta 在受测框架中最好；**代码生成能力是任务成败的关键**；长上下文处理与上下文感知的知识检索**仍是持续短板** |
| **PromptBio-Bench** | **244 个专家策划任务** | 三个 SOTA 生信 agent（含 Biomni、ToolsGenie）**准确率随任务难度显著下降** |
| **BixBench** | 53 个真实分析场景 | 要求 agent 在最少提示下自主完成分析 |
| 通用数据问答 | — | **最好的模型 pass@1 仅 38%** |
| 企业实际部署 | — | **实验室基准分与真实部署表现相差 37%** |

**一条对使用方式有直接影响的发现** **【检索】**：在能力增益上，
**self-reflection（自我复核）影响最大，其次是 RAG，再次是 planning。**

**【判断】** ⇒ **让 agent"先做再自查"比让它"先规划再做"收益更大。**
这与很多人的直觉相反，也与"写个漂亮的计划就放手"的用法相反。

## §2 四类失败原型 —— 以及它们在本机的真实对应

**文献总结的四类 agent 失败原型** **【检索】**：
① premature ungrounded action（未落地就动手）
② over-helpfulness with plausible but incorrect details（过度帮忙，细节貌似合理实则错误）
③ distractor-induced context pollution（被干扰项污染上下文）
④ fragile execution under load（负载下执行脆弱）
且**成功率随复杂度与任务时长呈超线性衰减**。

**下表把它们对上本机真实发生过的案例——抽象的失败模式配上具体案例才防得住。**

| 原型 | 本机真实案例 **【本机】** | 已有的对策 |
| :--- | :---: | :---: |
| ① **未落地就动手** | 请求里出现"这个位置""本文"等无 path 指代时，跑去全局 `grep` 而不是解析成当前打开的文档 | `resolve_current_doc.py` hook 自动注入解析好的路径 |
| ② **过度帮忙 + 貌似合理的错细节** | **本会话**：断言"`font.sans-serif` 里 DejaVu 在后会逐字形回退"——**实测相反**，回退只发生在 `font.family` 写成具体字体名列表时（见 [`../../software_pitfalls/matplotlib_cjk_font.md`](../../software_pitfalls/matplotlib_cjk_font.md) §2.1） | **动笔前先跑一次验证**；机制类断言一律实测 |
| ② 同类 | 凭印象断言"某源上没有 LeafCutter 这个包"，导致**五轮编译白工**；实际 bioconda 有现成的 2.0.3 | 规则：**「某源上没有这个包」必须先跑一次 search 再断言** |
| ③ **上下文污染** | 同一批判读图存在同名多版本，打开缺陷版看到"零证据"、有效版看到"20 条成簇读段"，**结论完全相反** | 规则：同名多版本必须显式警告并说清哪个是当前有效版 |
| ④ **负载下脆弱** | 一夜之间下游 4 步里 3 步静默失败，看门狗只守着 sarek 没守编排链 | 长任务一律进 tmux + Phase-2 看门狗常驻 |
| **⑤ 本机自己发现的第五类** | **假通过检测器**：用 logging handler 去抓 matplotlib 的缺字形告警，而**告警走的是 `warnings` 模块** ⇒ 无论好坏都打印 0，"验证通过"是假的 | **检测器必须先证明能报出真阳性** |
| **⑥ 本机自己发现的第六类** | **零结果当结论**：DEXSeq 报"0 个显著"，实际真值 **9301 个**——跨对象 `match()` 取过滤字段导致整列 NA，零报错且长得像生物学结论 | **「0 个/空结果」当结论前必须先证明分母不是 NA** |

**【判断】** ⑤⑥ 这两类在通用 agent 文献里没有单列，但在生信里**危害最大**——
因为它们的产物**看起来完全正常**，而且**方向是"更干净的结果"**（没有告警、没有显著基因），
恰好是人最不会去质疑的方向。

## §3 环节分级：绿 / 黄 / 红

| 分级 | 环节 | 为什么 |
| :--- | :---: | :---: |
| 🟢 **绿：可以交，验证成本低** | 写/改分析脚本、写管线编排、环境与依赖排查、把一份表转成另一种格式、批量重命名与整理、写文档初稿、代码审查、复现别人的报错 | **跑一遍就知道对不对**；失败是响亮的（报错、退出码非零） |
| 🟡 **黄：可以交，但必须配闸门** | QC 报告解读、图件生成、参数选择、统计方法选择、结果表的汇总统计、报告正文起草 | 失败**不响亮**：图能画出来但含义错、统计能跑完但口径错。**需要 §4 的闸门** |
| 🔴 **红：不要交** | 从图像转录数值、最终结论的科学判断、客户沟通的定稿与发送、任何"阴性结果"的定性、删除/覆盖既有产物 | 失败**完全静默**，且后果不可逆 |

**【判断】** 关于 🔴 里的"阴性结果的定性"：这是本机最惨痛的一类
（§2 表格里的 ⑥）。**"没找到"这个结论，永远需要一个独立证据证明"如果有，我能找到"**——
本机的标准做法是**交换样本角色反向跑一遍同一流程**，用反向产出当本底。

## §4 闸门设计：让"错了"变成"响亮的错"

**这一节是本篇的实操核心。** 判据：**每一个交给 agent 的黄区任务，
都必须有一个"错了会自己叫出来"的机制**。

### 4.1 四种闸门，从弱到强

| 强度 | 形式 | 例子 |
| :--- | :---: | :---: |
| 弱 | **人工复核** | 交付前自己看一遍 |
| 中 | **要求 agent 给回读命令 + 输出** | 不接受"已完成"，只接受"我跑了 X，输出是 Y" |
| 强 | **脚本内断言** | `assert_all_points_visible()`、`assert_yaxis_flipped()`、数据行守恒断言 |
| **最强** | **harness 级 hook（机械化）** | 写文件时自动检查、Stop 时自动自检、危险命令自动拦截 |

**【本机】** 本机已经把六类检查机械化成 hook（`~/.claude/hooks/`），
覆盖破坏性命令拦截、交付文件覆盖告警、无 path 指代解析、报告/邮件判据、回复自检。
**这是"最强"档的现成范例**——它的价值在于**不依赖任何人记得**。

### 4.2 三条通用闸门（任何黄区任务都适用）

1. **不接受状态断言，只接受回读输出**
   "字体已修好" ❌ → "跑了渲染 + `warnings` 捕获，缺字形告警 0 条，`font.family=[...]`" ✅
   **本机已把这条做成 Stop hook：状态类断言必须配对回读命令的输出。**

2. **检测器必须先证伪自己**
   任何"检查通过 / 0 个问题"的结论，**先用一个已知的坏例子跑一遍**，
   确认检测器会报警。**报不出真阳性的检测器等于没有检测。**

3. **同一事实出现两处，就必须有比对**
   数字在报告与表格各写一次、坐标在两个脚本各算一次——**必须有一步显式比对**，
   否则漂移是静默的。

### 4.3 针对单细胞/空间的专用闸门 **【判断】**

| 环节 | 闸门 |
| :--- | :---: |
| 任何散点/PCA/UMAP | **数点数**：绘图前后的细胞数必须相等（形状 aes 超过 6 个水平会静默丢点） |
| 空间图 | **y 轴方向断言**：图像坐标系与绘图坐标系 y 轴相反，翻转后图看起来完全正常 |
| 拆包/取子集 | **聚合统计量逐包重算**，不许沿用全量的数字 |
| 差异表达 | **报 0 个显著时，先证明分母不是 NA**（§2 的 ⑥） |
| 注释/整合 | **不该变的有没有变**：阴性对照基因、已知应分开的群 |

## §5 怎么写指令（对 agent 的输入）

**【判断】** 基于 §1 那条"self-reflection 收益最大"的发现，最有效的指令结构是：

1. **给判据，不给步骤**。"把中文字体修好"不如"修完后 `warnings` 通道的缺字形告警必须为 0，
   把命令输出贴出来"——**后者自带验收标准**。
2. **明确要求先证伪**。"先构造一个会失败的例子，证明你的检查能抓到它。"
3. **划定范围**。哪些文件可动、哪些绝对不动。**范围不划，②③ 两类失败必然发生。**
4. **要求区分"实测"与"推断"**。本机通行的做法是逐条标注
   **【检索】/【判断】/【未验证】**，让读者能分别对待。
5. **长任务先说清副作用**：预计耗时、会写哪些目录、中途打断会发生什么——
   **让"打断"永远是安全的**，人才敢在发现不对时叫停。

## §6 我不确定 / 有争议的地方

1. **§1 的基准数字来自不同论文、不同任务集，彼此不可直接比较** **【判断】**。
   "38% pass@1"与"37% 部署差距"是两个完全不同口径的数字，**不要相加或相互印证**。
2. **本篇 §2 的本机案例都是我自己参与的记录** **【判断】**——它们是真实的，但**选择性偏差存在**：
   我记住的是被抓到的失败，**没被抓到的失败按定义不在这张表里**。
3. **agent 能力迭代很快** **【判断】**，§1 的具体分数会过时；
   但 §0 的判据（"错了能否被机械检出"）与 §4 的闸门设计**不依赖模型能力**，应当更耐用。
4. **§4.1 "最强档"的 hook 方案是否可迁移到别人的环境** **【未验证】**——
   本机方案与 Claude Code 的 harness 绑定。
